# Indirect Prompt Injection via Financial Data Fields — Research Report (as of 2026-07-26)

## 1. Current OWASP guidance on indirect prompt injection — VERIFIED

The current edition remains **OWASP Top 10 for LLM Applications 2025 (v2.0)**, published 18 Nov 2024, still authoritative in mid-2026; OWASP maintains it continuously rather than annually ([genai.owasp.org LLM Top 10](https://genai.owasp.org/llm-top-10/); [OWASP 2025 PDF](https://owasp.org/www-project-top-10-for-large-language-model-applications/assets/PDF/OWASP-Top-10-for-LLMs-v2025.pdf)). **Prompt Injection is LLM01** — the top risk. OWASP explicitly names **indirect prompt injection** (instructions embedded in documents, web pages, or other ingested content) as a distinct and subtler vector than direct injection. A complementary **OWASP Top 10 for Agentic Applications 2026** was published separately for autonomous-agent risks ([genai.owasp.org agentic](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)).

OWASP's recommended mitigations for LLM01: constrain model behaviour and role; **separate and clearly denote untrusted content**; enforce **least-privilege tooling**; input/output filtering; **human approval for high-risk actions**; and regular adversarial testing / treating the model as an untrusted user. Notably, OWASP frames these as risk reduction, **not elimination** ([Mend guide](https://www.mend.io/blog/2025-owasp-top-10-for-llm-applications-a-quick-guide/); [Oligo](https://www.oligo.security/academy/owasp-top-10-llm-updated-2025-examples-and-mitigation-strategies)).

## 2. Attacks via transaction memos / payment-reference fields — VERIFIED

This is now documented as both research and in-the-wild:

- **"The One-Cent Attack: Prompt Injection Through Bank Transfer Memos"** (Developers Digest) demonstrates transferring a trivial amount (€0.02) with a prompt-injection payload in the **SEPA free-text description field**. Because the memo is stored in the victim's own transaction history and later surfaced by the bank's assistant, the payload arrives through a **highly trusted channel** (the bank's own app). In the PoC the assistant was coerced into generating a **credible in-app phishing "reauthentication" message** referencing the user's real account context ([developersdigest.tech](https://www.developersdigest.tech/blog/ai-agent-prompt-injection-banking)).
- **Blue41** describes hardening a European bank's financial AI assistant, explicitly listing transaction descriptions, payment references, and merchant metadata as attacker-controllable fields ([blue41.com](https://blue41.com/blog/securing-a-european-banks-financial-ai-assistant/)).
- **In-the-wild financial exploitation (adjacent):** Zscaler ThreatLabz (July 2026) documented **live campaigns** using CSS-hidden instructions and JSON-LD/schema metadata to make AI agents send **crypto payments to hardcoded wallets**; a related incident drained ~$175,000 in DRB tokens via an agent-linked trading platform ([SecurityWeek](https://www.securityweek.com/prompt-injection-attacks-trick-ai-agents-into-making-crypto-payments/); [Unit 42](https://unit42.paloaltonetworks.com/ai-agent-prompt-injection/); [SC Media](https://www.scworld.com/news/malicious-websites-trick-ai-agents-into-crypto-payments-context-poisoning)).
- **Empirical prevalence:** *"Indirect Prompt Injection in the Wild: An Empirical Study"* ([arXiv:2604.27202](https://arxiv.org/pdf/2604.27202)) confirms IPI is "no longer merely theoretical" but actively weaponized across real telemetry.

**Assessment:** The specific memo/reference-field vector is **VERIFIED** as a demonstrated, credible attack class; large-scale exploitation *specifically through bank memo fields* is **PARTIAL** (strong PoCs and one bank engagement; broad in-the-wild financial exploitation is documented mainly via web/crypto channels rather than confirmed mass memo-field campaigns).

## 3. Defense effectiveness data — VERIFIED (with caveats)

- **Spotlighting (Microsoft, [arXiv:2403.14720](https://arxiv.org/pdf/2403.14720)):** delimiting, datamarking, encoding. Datamarking cut ASR from ~50% to **<3%** (GPT-3.5) and 40%→**0%** (text-003); encoding reached **~0%** on summarization/QA. Now surfaced in **Azure Prompt Shields** (Build 2025).
- **Instruction hierarchy (OpenAI, [openai.com](https://openai.com/index/the-instruction-hierarchy/)):** +63% robustness to system-prompt extraction, **>30%** improvement in jailbreak robustness, with generalization to unseen attacks. Deployed in GPT models. Reduces but does not eliminate.
- **Classifier defenses — Meta PromptGuard 2 / LlamaFirewall:** 97.5% recall @1% FPR; alone cut ASR 17.6%→7.5%, and **~90% ASR reduction (to 1.75%)** stacked with other defenses. **Caveat:** Azure Prompt Shield and Meta Prompt Guard have been **evaded at up to 100%** via character injection / adversarial techniques ([arXiv:2504.11168](https://arxiv.org/html/2504.11168v1); [arXiv:2510.01529](https://arxiv.org/pdf/2510.01529)).
- **CaMeL — "Defeating Prompt Injections by Design" (DeepMind, [arXiv:2503.18813](https://arxiv.org/pdf/2503.18813)):** capability/data-flow isolation with a privileged planner LLM never exposed to untrusted data. Solves **77%** of AgentDojo tasks *with provable security* (vs 84% undefended), a structural rather than probabilistic guarantee.
- **Design Patterns paper ([arXiv:2506.08837](https://arxiv.org/abs/2506.08837), Beurer-Kellner et al., Jun 2025):** six patterns — Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual-LLM, Code-Then-Execute, Context-Minimization — all built on **isolating untrusted input and constraining agent capability**.
- **2026 state of the art:** MELON (ICML 2025) reported **0.32% ASR at 68.72% utility** on GPT-4o ([Zylos](https://zylos.ai/research/2026-04-12-indirect-prompt-injection-defenses-agents-untrusted-content/)); the CSA "in the wild" note confirms operational escalation ([CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-indirect-prompt-injection-in-the-wild-2026/)).

## 4. Fact-check D6 (no defense is complete; structural avoidance is primary) — VERIFIED

The consensus holds. Per 2025 statements from **OpenAI, Anthropic, and Google DeepMind**, prompt injection **cannot be fully solved within current LLM architectures** (summarized in [Zylos](https://zylos.ai/research/2026-04-12-indirect-prompt-injection-defenses-agents-untrusted-content/)). **Simon Willison's "lethal trifecta"** (16 Jun 2025) — private data + untrusted content + external communication — argues the fix is **architectural: break the trifecta and enforce least privilege**, because "architecture beats any prompt-level instruction" ([simonwillison.net](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). OWASP, the Design Patterns paper, and CaMeL all converge on the same principle: **structurally prevent the model from seeing/acting on raw untrusted text on critical paths** rather than trying to detect every malicious string. Detection/filtering is a defense-in-depth layer, never a complete solution ([airia](https://airia.com/ai-security-in-2026-prompt-injection-the-lethal-trifecta-and-how-to-defend/)).

## Concrete mitigations for our architecture

**Analytics path (never exposes raw descriptors) — primary, structural.** Aligns with CaMeL / Plan-Then-Execute. Compute aggregations (sums, categories, trends) over **structured, typed fields**; the LLM narrating results should receive only numeric/categorical outputs and canonical category labels — **never raw memo/reference strings**. This removes the untrusted-content leg of the trifecta from the highest-privilege path.

**Enrichment path (categorization/merchant lookup) — constrain capability.** Treat descriptor text as untrusted. Use an **isolated, tool-less classifier** (Map-Reduce / Dual-LLM pattern) whose *only* output is a constrained enum (category ID, merchant ID, confidence) — a **quarantined LLM that cannot emit free text, call tools, or reach private data or external endpoints**. Validate its output against an allowlist; reject anything off-schema. Apply spotlighting (datamarking/delimiting) as a secondary layer here.

**Narrator input sanitization — defense in depth, not the primary control.** If the user-facing narrator must ever echo a descriptor, pass it as **explicitly delimited/datamarked untrusted data**, strip control/formatting characters, cap length, and run a classifier (Prompt Shields / PromptGuard-class) — while assuming classifiers are bypassable (up to 100% evasion documented), so this never gates a high-risk action.

**Cross-cutting:** least privilege on all tools; **human confirmation for any money-moving or messaging action**; the component touching untrusted descriptors must not simultaneously hold private-data access and an external-comms channel; adversarial/red-team testing including memo-field payloads.
